Building a real-time investment analysis engine

Building an investment platform that powers a biotech hedge fund as successful as Perceptive is a real challenge. The platform needs to provide enough value and be well-designed enough so that investors utilize it as part of their research process rather than play around with it as a fancy demo.

Why it is valuable

The key parts of the product that make it valuable are as follows:

It does things humans can’t

  • Scraping the open internet, getting information that analysts don’t uncover with standard Google searching
  • Evaluating new available information every day, for ex. parsing a new clinical FDA trial instantly rather than requiring a human to manually go through to read it and understand it
  • Stress-testing numerous theses against new data instantly, rather than requiring a human to reason through all scenarios and update existing investment memos

It is auditable and understandable

  • If Perceptive prides itself on being an impartial, value-focused investor, the technology we use should not introduce its own bias
  • Every argument/dataset/estimate that is either retrieved or generated should be traceable to its source material, so we can understand exactly what contributes to our eventual investment decision making
  • If a regulator comes and accuses us of using MNPI, we have an auditable stack to show what we’ve used as part of our research process
  • We can modify our tools (GenAI models) behaviors to trial out different research hypotheses, so we clearly know how we come to the right conclusions
  • Given these characteristics, I have architected the following platform. Keep in mind this is only 3 days of work and is merely a demo that shows what is the art of the possible within a firm like Perceptive. Deployment

  • Deployed on Render as two services: a FastAPI read API and a Next.js web app.
  • Committed data snapshot (corpus, ledger, one memo per company), so the API and app run from a clone with no key. A key is only needed to write a new memo.
  • Built in-house: the BM25 retriever, the grounding and evaluation harness, and the ledger. The memo engine's only off-the-shelf Python dependency is click; the read API and web app use FastAPI and Next.js.
  • Highlight and comment. In the web app an analyst can highlight any passage of a memo and leave a comment on it. A short intake agent captures the note and writes it to the ledger, so every piece of feedback is recorded and traceable.
Ingestion

In order to keep Perceptive at the forefront of investing, I wanted to explore the possibility of building a system that can answer questions about the companies we’re interested in based on the most recent information in the world. For example, a new FDA trial comes out, we may ask “how does that affect our existing investments?” If a portfolio company published their financials, we ask “how can we compare this to their previous performance?” In order to do this, we need to consistently be pulling the latest information from the open internet from a number of sources. This demo pulls information from:

  • SEC EDGAR — company filings (10-K, 10-Q, 8-K, etc.)
  • SEC EDGAR XBRL (companyfacts API) — structured numeric financials
  • ClinicalTrials.gov (v2 API) — trial registrations and results
  • openFDA — drug labels, FAERS adverse events, Drugs@FDA
  • PubMed (NCBI E-utilities) — published literature
  • Europe PMC — preprints (bioRxiv/medRxiv)
  • PubChem (PUG-REST) — compound/chemistry data
  • CDC (data.cdc.gov) — common-disease epidemiology
  • Orphanet / Orphadata — rare-disease prevalence
  • CMS Medicare Part D — Spending by Drug
  • CMS Medicare Part B ASP — Average Sales Price pricing
  • Medicaid NADAC — National Average Drug Acquisition Cost

To do this, this demo uses an ingestion script that polls these sources and ingests the latest entries via an API endpoint. Currently, it’s driven by a CLI command, but we’d want to set this up as a cron-job that runs every day automatically.

Retrieval-augmented generation

Ingestion helps us solve the problem of getting all of the data we need. But now we need to utilize it as part of our investment process. How can we get an analyst to see the information they need? If we utilize LLMs like Claude and ChatGPT to build theses of an investment memo, how can we get them to work with the latest information we have?

The system that helps us build this is called retrieval-augmented generation (RAG). It’s fairly self-explanatory, we augment the generation that the large-language model does by retrieving certain information.

Retrieval-augmented generation is actually a simple system. It goes through the following steps:

  1. Indexing
    • We grab all of the information that we have in our corpus (EDGAR, Clinical Trials, …) and build a searchable index over it.
    • The standard approach is to generate “embeddings”, a vectorized representation of the underlying data, and index those.
    • For this demo I used a simpler lexical index, Best Match 25 (BM25), instead of embeddings. Either way, indexing lets us search far faster than a sequential scan over all of the data (this is essentially how the Google search engine works).
    • The outcome is a searchable index of all of the data we have that we can give query words, for example “glp1 pills” and get all documents related to glp1s in an efficient fashion.
  2. Retrieval
    • Retrieval is the first step that happens after we give the LLM a generation task.
    • The LLM gets a prompt like “Build me a memo on AbbVie based on its Humira drug”. It takes it and splits up the prompt to query the index for all documents related to AbbVie, Humira etc.
  3. Generation
    • Take all of the results of retrieval, and provide it in the context of a LLM API call to create the desired result. Effectively ask the LLM to generate the desired response for us.
    • Prompt engineering has a large impact on this step, when it comes to generating the correctly formed result.
  4. Evaluation
    • Validate that the response has the desired format and structure.
    • Validate that the response retrieved the desired documents from the corpus.

Optimizing RAG to specific workflows is a challenging task, and the machine learning/AI research space has hundreds of papers published on this topic just in the last two years. For context, here are some of the knobs you can turn to tweak how RAG performs:

  • Embeddings. I used standard lookup, but we can experiment with much fancier embeddings.
  • Chunking. Performed chunking based on document structure, for ex FDA trials.
  • Indexing. I used Best Match 25 (BM25) as an index.
  • Prompt engineering. Instructed the LLM to produce an investment memo with analysis around peak sales, drug efficacy etc.
  • Context sizes. Can potentially reduce the size of context passed into the model to “focus” the model or ensure that it gets more information from the retrieved documents.
Data estimates

The last component of the requested demo was to generate viable estimates for financial benchmarks for each company, for ex. peak sales, rNPV. For this, we utilize basic Python Numpy/Pandas calculations to compute our estimates based on the values extracted from the earlier RAG pipeline. This space needs investment to incorporate multiple methodologies of computing the correct financial estimates. For now, this is subpar compared to Excel DCFs for a company’s valuation. I touch on this in the follow-ups section.

Evaluation

Grading the memo against its sources

  • Every claim is checked against the evidence it cites.
  • Numbers are graded by code. A model judges only where the call is about language, and never grades a number.
CheckWhat it asksBy
RetrievalDoes the right passage come back for a querycode
Epidemiology groundingIs the population cited to a real source and in a sane rangecode
FaithfulnessIs each claim actually supported by what it citesjudge
Judge probesDoes the judge get known-answer cases rightjudge
Known-badDoes a memo with shuffled evidence score far worsejudge
CalibrationDoes the judge agree with a humanjudge

The judge is tested before its scores count

  • Faithfulness uses a model to read a model, so on its own it can flatter what it grades.
  • Known-answer probes check whether the judge gets clear cases right.
  • Known-bad feeds it a memo with the evidence shuffled and requires the score to drop by a clear margin. A scrambled memo that still scored well would mean the judge measures nothing, so this check runs first to make sure we are reducing the rate of generating false-positive memos.
  • Calibration compares the judge's verdicts to a human's and reports the agreement as a number.
  • A case the checks caught: the memo pulled a patient-population number from a real source, but it was the prevalence for the wrong disease. The epi check now catches this by making sure the number sits in a sensible range and by spotting counts that have been added up too broadly.
  • Limit: there is no free public feed of analyst consensus. The claim the brief cares about most, where the view departs from the market, is argued from evidence rather than scored against a number.

Follow-ups

The valuation math is an area we would invest more into

  • The calculations for producing the resulting financial estimates are correct. However, there's a wide range of assumptions for some of the values computed. For example, peak sales relies on an estimate for population penetration of a given drug, which can vary wildly. Nailing these values and grounding them in evidence is a problem that can be solved by effectively tuning RAG.
  • Another example is the probability of success number. This is the sort of prediction that an analyst figures out through their own rigorous methodology. Instead, we give a general estimate, most likely because of the model's own guess based on its pretraining data. Eventually, we would want to incorporate some of the research methodologies of Perceptive researchers to truly ground this number in concrete estimates.
  • We compute NPV primarily for the lead asset of a company, whereas most large biotech drug makers have multiple assets that drive significant portions of their revenue. Properly predicting the full estimate for a company's valuation relies on us modelling all assets, which is a natural extension of this demo, just one that we haven't gotten to yet.
Long-term vision

Where this goes

  • Re-run the memo automatically whenever a company files something new or reports trial data, so it always reflects the latest information.
  • Run it across many companies at once, so we can compare them and spot where our view differs most from the market's.
  • Incorporate valuation methodologies from research analysts at Perceptive themselves, so we can evolve our system to produce more reliable predictions over time that have the same investment rigor that we usually use, but always take advantage of the latest data that we've got.
  • Pull the actual charts behind a claim into the memo, connecting this back to the Stage 1 figure work. Make sure that all of these values are properly traceable within our system and provide users the ability to comment and point out issues with our computer vision text extraction over time.
  • Build a proper labeled test set that we hold out and check against human judgment, so a passing score actually means the memo is right. Our corpus being well fleshed out is crucial for us to build strong RAG and good investment theses over time.
  • Make it easy for analysts to comment and feed their edits back into the system, so our engine learns where memos are wrong and improves over time.
