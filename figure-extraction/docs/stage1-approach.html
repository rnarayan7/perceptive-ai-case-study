Approach

A challenge like this is a classic problem in computer vision. There have been countless studies and packages that focus on classification of each individual chart type listed in the problem statement. If one were to break each classification task into different subtasks, the subtasks would be: entity recognition, bounded box highlighting, and graph point clustering. Each one of these subtasks has a rich history of research focused on it in classical machine learning.

However, rather than diving into research and building bespoke classification systems for each image type, my general approach is to build infrastructure to utilize the latest models to classify the images, and later focus on building bespoke, specialized systems when necessary.

There are two key components to building a strong generalized classification system: models used for classification, and an evaluation dataset.

Eval dataset

Starting with the evaluation dataset, for this, we utilized the images given, as well as added some more annotated images to round out our dataset. The images were fetched from public datasets and are linked in the appendix.

Models

For selecting models, in most cases the likely correct answer is to throw it at a vision-language model provided by one of the model providers (Claude, ChatGPT). Vision-language models, like large language models, are actually an example of deep learning rather than classical machine learning. Internally, they chunk up images into small “tokens” and use them to understand the image passed to them, as well as generate new images. Since they can be used along with large-language models, they are the most versatile of models to start with.

Classic computer vision algorithms focus much more on tightly bounded problems like edge detection, bounded box highlighting, and so on. These can be valuable to us if used in the correct way. Not to mention, classic computer vision uncovered a number of necessary steps for improving classification accuracy like image preprocessing, pixel expansion, and so on.

Initial results

In terms of initial results. The VLM on its own performed well on some cases and badly on others. It correctly parsed Figure 5 (the results table) and performed well on Figure 1 (the Kaplan-Meier curve) and reasonably well on Figure 3 (the drug concentration plot). However, for Figures 2, 4, and 6, which all had bar charts and plots, the VLM struggled, correctly answering only about a third of the values on the waterfall and forest and none on the spider. Knowing this, we had to build a more specialized solution for these charts.

Architecture

I ended up trialing a number of approaches but ended up settling on a two-step architecture utilizing VLMs + deterministic computer vision.

The process looked like the following:

01
VLM reads the image and extracts text/numbers out of it, which it does well
02
VLM provides context on understanding of chart type to do calibration of axis
03
Model passes calibration from VLM to deterministic computer vision model
04
Deterministic computer vision model extracts bar lengths from image and reports numbers
05
Both results are verified against final dataset, one with just VLM, one with VLM + deterministic CV

VLM + deterministic CV was the better approach, yet we have a long way to go before it’s a truly generalizable system.

Challenges

There are a number of specific challenges that we ran into that still caused issues. Here are some of them:

  • Some images were too sparsely pixelated for the model to clearly see the difference between two bars
  • Some bars were too densely packed for the model to be able to identify the start of one versus the end of another
  • Some bars had different colors that were not explained by the chart legend, which made it difficult for the model (and even human) to interpret the correct answer
Improving the system

Given these challenges, if we endeavor to improve the system, this is how we should go about it. There are two fundamental components to further improving our classification:

  • Eval datasets
  • Different architectures

Eval datasets

Eval datasets are necessary for fundamentally improving this system over time. The main way we can improve our eval datasets is performing some human data labeling of images and adding more to our corpus of data. This way we can trial multiple approaches and confirm their performance on a wide set of images. This is a time-intensive, and admittedly boring first step to improving the performance of our system. We could take advantage of systems like Mechanical Turk (powered by Amazon) or Scale AI to acquire vast sets of correctly labeled images, but to a certain extent, the developer training this system will have to do some amount of manual verification to improve the amount of images in our corpus. However, with a full corpus, we have a ton of flexibility to attempt a number of interesting ideas, which I’ll cover in the next section.

Different architectures

For different architectural approaches, there are a lot of things that we haven’t yet tried due to a lack of time. I will list out the ideas I’ve had so far:

  1. Loop engineering
    • Give the model some general context on the image and allow it to execute tool calls itself in a long loop
    • Give the model a sandbox and allow it to write its own code for classification of the image
  2. Multi-agent verification
    • Right now, we have a single agent produce one response, but nothing to verify. We could set up another agent to continually verify output from the first agent.
    • This can be repeated from a number of different vectors. One agent for value verification, one agent for validating that we matched the correct CV calibration to the correct image type. By ensuring that each of these agents have limited information in their context window, each of their “judgment” is clearer.
  3. Specialized ML models
    • Most of what we have done has been LLM calls + some deterministic CV code. We haven’t used any specialized models trained on charts and graphs. The reason for this is that this is an expensive build from an engineering standpoint and requires significantly more compute to run. However, this can potentially yield better results if we, for example, used a model from HuggingFace’s open repository of CV models.
  4. Image preprocessing
    • We tried some rudimentary image expansion, but nothing to the full level of what we could accomplish.
    • Some other things we could try:
      • Pass image to a model with specific goal of sharpening image pixels and read only from the result
      • Try different image codecs when passing into the VLM
  5. CV templates
    • One other approach that I found quite effective midway through the project was utilizing pre-processed CV calibrations for each bar chart type. This had great performance until I realized that it was only going to work for these type of charts. In the real world with a broader set of chart formats, this sort of approach would fail.
    • However, if we managed to create a relatively exhaustive repository of CV calibrations to cover most of the chart types, we could have a model identify the calibration type from our list that we provide to it and match the image with the appropriate one. This could yield much better performance than trying to derive axes and other calibration details from scratch.
Takeaway

Overall, you can clearly see that there are a wealth of approaches to be tried to improve our system and build a truly generalizable image classification service for biotech charts. However, the key takeaway here is that we need to invest in a good foundation of evals to open the doors for us to try a number of approaches, and really help us nail down which are the most effective for this use case.
